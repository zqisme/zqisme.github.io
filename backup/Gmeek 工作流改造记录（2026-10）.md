记录一次博客构建流水线的整修：从反复失败的构建改到最小权限、增量优先的版本，顺带解决了「改配置不生效」和「关闭文章不下线」两个老问题。

## 起因

2026-10-27 手动触发 `build Gmeek`（run #943），`Generate blog` 在 6 秒时失败：

```
The version '3.8' with architecture 'x64' was not found for Ubuntu 26.04.
```

原因不是代码，而是环境漂移：

- workflow 里写死 `python-version: 3.8`（2024-10 已 EOL）；
- `runs-on: ubuntu-latest` 已经迁到 **Ubuntu 26.04**，不再提供 3.8 的预编译包。

回头看 Actions 记录，10-24 / 10-25 / 10-26 三次每日定时构建其实**全部是 failure**，只是一直没人察觉：`git push || echo` 把推送失败吞掉、日志全绿，站点停留在旧内容上。

## 修了什么

| 问题 | 原来 | 现在 |
| --- | --- | --- |
| 构建直接失败 | `python 3.8` + `ubuntu-latest` | `python 3.12` + 固定 `ubuntu-24.04` |
| Node 20 弃用 | checkout@v4 / configure-pages@v4 / setup-python@v5 | @v5 / @v6 / @v6（另 upload-pages-artifact @v5、deploy-pages @v5） |
| 权限过大 | `permissions: write-all` | build 仅 `contents: write` |
| 依赖漂移 | `-r requirements.txt`（裸包名） | 追加 `"PyGithub<3"` 兜住大版本 |
| 装 jq 可能挂起 | `sudo apt-get install jq` | 先 `command -v jq` 判断，且带 `-y` |
| 变量未加引号 | `[ $GMEEK_VERSION == 'last' ]` | `[ "$GMEEK_VERSION" = "last" ]` |
| 漏拷隐藏文件 | `cp -r ./*` | `rsync -a --exclude=.git` |
| token 进命令行 | token 作为脚本参数 | 先落到 `GH_TOKEN` 环境变量 |
| 推送失败被吞 | `git push \|\| echo "nothing to push"` | 有变更才提交，`pull --rebase` 后直接 push |
| 并发抢推 | 无 | 顶层 `concurrency`，构建可取消 |
| 无超时 | 无 | build 15 分钟 / deploy 10 分钟 |
| 中途失败不中断 | 无 | 每个 `run` 加 `set -euo pipefail` |

## 三个值得记住的点

**① 固定 runner 镜像，别追 latest**

`ubuntu-latest` 不是一个稳定的名字，它跟着 GitHub 的迁移走。这次就是被 26.04 迁移打了个措手不及。固定成 `ubuntu-24.04` 之后，镜像升级由自己控制，代价是到期要手动跟进。

**② 增量还是全量，取决于 Gmeek 会不会「看不见」这条 issue**

`runOne()` 里有一段：

```python
issue = self.repo.get_issue(int(number_str))
if issue.state == "open":
    ...重建这一篇...
else:
    print("====== issue is closed ======")   # 什么都不做
```

所以传了编号、但 issue 已关闭时它直接返回，旧文章会一直留在站点上。现在按动作分流：

```yaml
case "$EVENT_ACTION" in
  closed|deleted|transferred) ISSUE_NUMBER="" ;;   # 清空编号 → 全量重建
esac
```

编号为空时走 `runAll()`，而 `get_issues()` 只返回 open 的 issue，文章连同 HTML 一起消失。标签、置顶这类改动仍走增量，只重建受影响的那一篇。

**③ 不要再吞掉 push 失败**

`git push || echo` 会让所有推送问题变成绿灯：日志好看、仓库没更新、站点还是旧的 —— 最难查的那种故障。现在推送失败会让 job 变红，deploy 也会跳过。

## 现在的触发行为

| 操作 | 路径 | 生效时机 |
| --- | --- | --- |
| 新建 issue / 改标题正文 | 增量 | 立即 |
| 加标签 / 置顶 | 增量 | 立即 |
| 关闭 / 删除 / 转移 issue | 全量 | 立即（文章下线） |
| 改 `config.json` | 全量 | 立即（新增 push 触发） |
| 手动 dispatch（可填编号） | 增量或全量 | 立即 |
| 定时 | 全量 | 每周一 00:00（北京时间） |

## 备忘

- **发文必须带标签。** `createPostHtml()` 里有 `issue["labels"][0]`，无标签的 issue 会让构建报 `IndexError`。日常发文用 `笔记` 即可。
- **内容没变时不会产生提交。** `createFeedXml()` 在 RSS 除 `lastBuildDate` 外无变化时会沿用旧文件，schedule 触发也不重写 README。所以「定时构建没留下提交」是正常现象，不代表失败。
- **`GITHUB_TOKEN` 的推送不会触发 workflow**，因此 `push` 触发器不存在自循环风险。
- 定时任务在仓库连续 60 天无活动后会被 GitHub 自动停用。

## 待办
